# 0003. Integração contínua no GitHub Actions

- Data: 2026-09-21
- Status: **aceita**

## Contexto

Item 0.3 do `docs/PLANO.md`: "CI: lint, tipos, testes e build a cada push". A ferramenta já está decidida (**D9** / ADR 0001: GitHub Actions) e não é reaberta aqui — este ADR desenha o **pipeline**.

O que já existe (item 0.2, commit `579aa82`):

- `package.json` com `lint`, `format:check`, `typecheck`, `test:unit`, `test:e2e`, `test:e2e:prints`, `build` e `verificar` (encadeia os cinco primeiros); `engines.node >= 22`; `package-lock.json` versionado.
- `playwright.config.ts` com os projetos `iphone-webkit` e `android-chromium` (**D3**), `forbidOnly`/`retries: 2`/`workers: 1`/`reporter: github+html` quando `process.env['CI']` está definido, e `webServer` que roda `npm run build && npm run preview` em `http://localhost:4173`.
- `e2e/placeholder.spec.ts`: um único teste `test.skip`, criado só para validar a configuração dos projetos. Será substituído no item 0.4 (pendência 11 do plano).
- Dois testes unitários reais (`src/compartilhado/identificador.test.ts` e `dinheiro.test.ts`).
- `.github/workflows/` existe com um `.gitkeep`.
- `.gitattributes` com `* text=auto eol=lf` — o desenvolvimento é no Windows e o runner é Linux.

Restrições que o pipeline precisa respeitar:

- **Princípio 6 / privacidade**: nada de serviço de terceiros (Codecov, Sentry, Lighthouse CI hospedado, ações de autor desconhecido). O único fluxo aceito é GitHub Actions → Cloudflare Pages.
- **D8**: o fluxo do projeto é **commit e push direto em `origin main`**, sem pull request obrigatório. Isso condiciona os gatilhos e a recomendação sobre proteção de branch.
- **D10 / item 0.9**: o deploy é feito pelo **próprio Cloudflare Pages**, pela integração com o GitHub (build Vite, saída `dist/`). O CI **não** faz deploy e **não** guarda token nenhum.
- **D6**: os prints de fase são gerados sob demanda pelo `testador`/orquestrador (`npm run test:e2e:prints`) e ficam versionados em `docs/prints/fase-N/`. **Não** são responsabilidade do CI.
- O repositório é **privado** (criado pelo `setup.mjs`), então minutos de Actions e armazenamento de artefatos são limitados no plano gratuito. O pipeline precisa ser enxuto.

Estado das ferramentas verificado em 21/09/2026 (fontes ao fim):

| Item | Situação hoje | Efeito na decisão |
|---|---|---|
| `actions/checkout` | major atual **v7** (ESM, recusa checkout inseguro de fork por padrão) | usar `@v7` |
| `actions/setup-node` | major atual **v7**; `cache: npm` continua válido | usar `@v7` com `cache: npm` |
| `actions/upload-artifact` | major atual **v7**; aceita `retention-days` e `if-no-files-found` | usar `@v7` |
| Node.js | **v24 (Krypton) é Active LTS**; v26 é Current; v22 é Maintenance LTS | fixar `node-version: 24` |
| Playwright | 1.63.0; `npx playwright install --with-deps <navegador>` instala só os navegadores pedidos | instalar apenas `webkit` e `chromium` |

## Decisão

### 1. Um arquivo, dois jobs

`.github/workflows/ci.yml`, com:

- **`verificar`** — lint, formatação, tipos, testes unitários e build. É o portão rápido (estimado 2 a 4 min).
- **`e2e`** — Playwright em WebKit (iPhone) e Chromium (Android), com `needs: verificar`.

**Por que dois jobs e não um só:** o `e2e` gasta a maior parte do tempo baixando navegadores e subindo o servidor de preview. Separado e com `needs`, ele nem começa quando o código está quebrado no básico, e a aba Actions mostra em qual camada falhou sem abrir o log. O preço é um `npm ci` a mais — segundos, com o cache do npm quente.

**Por que o e2e entra no CI já agora, mesmo só tendo o placeholder:** hoje ele custa pouco (um teste `skip`) e evita que o item 0.4 precise voltar a mexer no CI. Com a suíte real, o gasto passa a ser justificado por **D3** — sem teste manual até o fim, um problema de WebKit só aparece se alguém rodar WebKit a cada push. Se o item 0.4 fizer o job passar de ~8 min, vale reavaliar (ver "Alternativas").

### 2. Gatilhos

```yaml
on:
  push:
    branches: [main]
    paths-ignore: ['**/*.md', 'docs/**', '.claude/**']
  pull_request:
    branches: [main]
    paths-ignore: ['**/*.md', 'docs/**', '.claude/**']
  workflow_dispatch:
```

- **`push` em `main`** é o gatilho principal: é assim que o projeto trabalha (**D8**).
- **`pull_request` para `main`** fica ligado porque custa zero hoje e cobre o caso de uma branch de experimento com PR (que também é o que gera o preview por branch do Cloudflare, **D10**). Como o `push` está restrito a `main`, não há execução dupla: branch com PR roda pelo `pull_request`, `main` roda pelo `push`.
- **`workflow_dispatch`** permite reexecutar o pipeline pela interface sem criar commit vazio.
- **`paths-ignore`**: este projeto faz muitos commits só de documentação (`docs/PLANO.md`, ADRs, prints, prompts de agente). Rodar build e Playwright neles é desperdício de minutos num repositório privado. O filtro só pula quando **todos** os arquivos do push casam com os padrões; um commit que mexe em `src/` e no `PLANO.md` roda normalmente. Mudanças no próprio `.github/` rodam.

### 3. Permissões, concorrência e runner

- `permissions: contents: read` no topo (menor privilégio; o job não escreve no repositório e não precisa de token de pacote).
- **Nenhum `secrets.*` é referenciado.** O deploy é do Cloudflare Pages, pela integração com o GitHub; nenhum token entra no repositório.
- **Só ações oficiais `actions/*`.** Ação de terceiro é código executando com acesso ao repositório — colide com o princípio 6. Regra permanente: se uma ação não começar com `actions/`, ela não entra.
- `concurrency` por ref, com `cancel-in-progress` **só fora da `main`**: numa branch, o push novo cancela o anterior; em `main`, cada commit fica com seu resultado próprio (o histórico de saúde da `main` importa).
- `runs-on: ubuntu-latest`. Se uma troca de imagem quebrar as dependências do WebKit, fixar `ubuntu-24.04` e registrar no plano.
- `timeout-minutes` em cada job (15 e 30), para um travamento não consumir a cota.

### 4. Cache

- **`actions/setup-node` com `cache: npm`** (chave derivada do `package-lock.json`). É o mínimo e o suficiente: restaura o cache do npm, e `npm ci` continua instalando a partir do lockfile — determinístico.
- **Sem cache de `node_modules`.** Cachear a pasta instalada pula a verificação do lockfile e é fonte clássica de "funciona no CI, quebra local".
- **Sem cache dos navegadores do Playwright por enquanto.** Guardar `~/.cache/ms-playwright` exigiria uma chave versionada à mão e ainda assim `install-deps` (pacotes APT) roda toda vez, que é metade do custo. Com um teste `skip`, otimizar agora é abstração para um caso só. **Gatilho de reavaliação:** quando o job `e2e` passar de 8 minutos (provável no item 0.4), acrescentar `actions/cache` com chave `playwright-${{ runner.os }}-<versão do @playwright/test no lockfile>` e trocar o passo por `install-deps` + `install` condicional.

### 5. O que fazer quando falha

1. **O job falha e a execução fica vermelha no commit.** Nenhum passo usa `continue-on-error`.
2. Dentro do job `verificar`, os passos de verificação usam `if: ${{ !cancelled() }}`: se o lint falhar, formatação, tipos, unitários e build **ainda rodam**, e o log mostra todos os problemas de uma vez. Um passo com `if` perde o `success()` implícito, então o job continua; a conclusão do job continua sendo "failure" porque um passo falhou. Isso existe para o agente que for corrigir fazer uma rodada só em vez de cinco.
3. O job `e2e` guarda `playwright-report/` e `test-results/` como artefato **apenas quando falha** (`if: ${{ failure() }}`, `retention-days: 7`). Artefato em execução verde só gasta os 500 MB do plano gratuito.
4. **Proteção de branch é configuração do GitHub e só o usuário tem acesso.** Recomendação registrada em "Pendências" abaixo — e ela não é obrigatória para o CI funcionar.

### 6. Guarda de dependência proibida

Um passo de três linhas falha o build se `dexie-cloud-addon` aparecer no `package-lock.json`. O ADR 0001 proíbe o pacote (sincronização paga, manda dado para fora); deixar essa proibição só em texto significa depender de alguém lembrar dela em toda revisão. É a única regra de privacidade que dá para verificar com um `grep` — as outras continuam com o `revisor-critico`.

### 7. `.github/workflows/ci.yml` (conteúdo exato)

```yaml
name: CI

on:
  push:
    branches: [main]
    paths-ignore: ['**/*.md', 'docs/**', '.claude/**']
  pull_request:
    branches: [main]
    paths-ignore: ['**/*.md', 'docs/**', '.claude/**']
  workflow_dispatch:

# Menor privilegio: o CI so le o repositorio. Nao ha deploy nem secret aqui:
# o deploy e feito pela integracao do Cloudflare Pages com o GitHub (ADR 0001).
permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  # Em branch, o push novo cancela o anterior. Em main, cada commit guarda seu resultado.
  cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}

jobs:
  verificar:
    name: Lint, formatacao, tipos, unitarios e build
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Baixar o codigo
        uses: actions/checkout@v7

      - name: Preparar Node 24 (Active LTS)
        uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm

      - name: Instalar dependencias
        run: npm ci

      # Os passos abaixo usam `!cancelled()` de proposito: o primeiro erro nao esconde
      # os seguintes, e quem for corrigir ve tudo numa rodada so.
      - name: Dependencia proibida (ADR 0001)
        if: ${{ !cancelled() }}
        run: |
          if grep -q '"node_modules/dexie-cloud-addon"' package-lock.json; then
            echo "::error::dexie-cloud-addon e proibido pelo ADR 0001 (sincronizacao paga, envia dados para fora do dispositivo)."
            exit 1
          fi

      - name: Lint
        if: ${{ !cancelled() }}
        run: npm run lint

      - name: Formatacao
        if: ${{ !cancelled() }}
        run: npm run format:check

      - name: Tipos
        if: ${{ !cancelled() }}
        run: npm run typecheck

      - name: Testes unitarios
        if: ${{ !cancelled() }}
        run: npm run test:unit

      - name: Build
        if: ${{ !cancelled() }}
        run: npm run build

  e2e:
    name: E2e (WebKit/iPhone e Chromium/Android)
    needs: verificar
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - name: Baixar o codigo
        uses: actions/checkout@v7

      - name: Preparar Node 24 (Active LTS)
        uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm

      - name: Instalar dependencias
        run: npm ci

      # So os dois navegadores de D3. Nada de firefox.
      - name: Instalar navegadores do Playwright
        run: npx playwright install --with-deps webkit chromium

      # O servidor de preview sobe pelo `webServer` do playwright.config.ts
      # (`npm run build && npm run preview`). Os prints (D6) ficam de fora: sao
      # gerados sob demanda pelo `npm run test:e2e:prints` e versionados no git.
      - name: Testes e2e
        run: npm run test:e2e -- --grep-invert "@prints"

      - name: Guardar relatorio do Playwright
        if: ${{ failure() }}
        uses: actions/upload-artifact@v7
        with:
          name: playwright-report
          path: |
            playwright-report/
            test-results/
          retention-days: 7
          if-no-files-found: ignore
```

O `.gitkeep` de `.github/workflows/` é removido no mesmo commit.

### 8. Contrato para os itens seguintes

| Item | O que o CI exige |
|---|---|
| 0.4 (suíte real) | `e2e/placeholder.spec.ts` sai; os testes novos precisam passar em **ambos** os projetos, ou pular explicitamente (`test.skip(({ browserName }) => browserName === 'webkit')`, pendência 10). Nenhuma mudança no `ci.yml` deve ser necessária. |
| 0.13 (prints, D6) | Todo teste de `e2e/prints.spec.ts` leva a **tag `@prints` no título** (ex.: `test('hoje @prints', ...)`), porque o CI o exclui com `--grep-invert "@prints"`. Print é entregável de fase, gerado à mão, não verificação de push. |
| 0.9 (deploy) | Nada entra neste workflow. O Cloudflare Pages constrói por conta própria a partir do GitHub. Se um dia o deploy passar a ser feito por Action, isso vira um ADR novo, com a discussão de onde guardar o token. |
| Qualquer item | Script novo no `package.json` que precise rodar a cada push tem que ser adicionado **aqui e no `verificar`**, para o local e o CI não divergirem. |

### 9. Critérios de aceite do item 0.3

O `dominio` só declara o item pronto quando todos passarem:

1. `.github/workflows/ci.yml` existe com o conteúdo da seção 7 e o `.gitkeep` da pasta foi removido; `npm run format:check` continua passando (o Prettier formata YAML — se ele reclamar do arquivo, rode `npm run format` e verifique que o conteúdo **semântico** não mudou).
2. Um push em `main` que toque `src/` (ou o próprio `ci.yml`) dispara a execução, e **os dois jobs terminam verdes** na aba Actions, com o `e2e` executando depois do `verificar`.
3. **Falha proposital é vermelha.** Numa branch descartável (`ci/prova-de-falha`) com PR aberto para `main`, um erro de lint plantado (ex.: `const x = 1;` sem uso, ou `console.log('x')`) faz o job `verificar` falhar **no passo "Lint"**, e os passos "Formatacao", "Tipos", "Testes unitarios" e "Build" **ainda aparecem executados** no log (prova do `!cancelled()`). Fechar o PR e apagar a branch depois. Registrar a URL da execução no relatório.
4. Erro de tipo proposital (ex.: `const n: number = 'a';`) falha o passo "Tipos"; um `expect` invertido num dos testes de `src/compartilhado/` falha o passo "Testes unitarios". Pode ser verificado localmente pelo código de saída (`npm run typecheck`, `npm run test:unit` terminam diferente de 0) — o CI só executa esses mesmos comandos.
5. O job `e2e` mostra no log `npx playwright install --with-deps webkit chromium` baixando **apenas** WebKit e Chromium, e `playwright test` reportando os projetos `iphone-webkit` e `android-chromium` (hoje, 1 teste pulado em cada).
6. Nenhum `uses:` do arquivo aponta para fora de `actions/`; a string `secrets.` não aparece no arquivo; `permissions: contents: read` está presente.
7. Um push só de documentação (ex.: mexer apenas em `docs/PLANO.md`) **não** dispara execução.
8. Reexecutar a mesma execução ("Re-run all jobs") dá o mesmo resultado (determinismo do `npm ci` + lockfile).
9. Tempos anotados no relatório: `verificar` e `e2e`, com cache frio e quente. Se `e2e` passar de 8 min, abrir a pendência de cache de navegadores da seção 4.
10. `git status` limpo depois do commit: o único arquivo novo é `.github/workflows/ci.yml` (mais a remoção do `.gitkeep` e a mudança de status no `docs/PLANO.md`).

## Alternativas consideradas

- **Um job único chamando `npm run verificar`.** Mais curto, e é o comando que o humano roda. Recusado por dois motivos: o log vira um bloco só (`&&` encadeado para na primeira falha e a aba Actions não diz qual etapa quebrou) e não dá para aplicar o `!cancelled()` por etapa. O `verificar` continua sendo o atalho local; o CI reproduz a mesma lista, em passos separados. O critério de aceite 9 da seção 8 (script novo entra nos dois lugares) existe justamente para eles não divergirem.
- **E2e fora do CI, só local, até o item 0.4.** Economizaria uns 4 minutos por push agora. Recusado: obrigaria a mexer no `ci.yml` de novo daqui a um item, e o custo atual é irrisório (um teste `skip`). Continua valendo como plano B se o item 0.4 deixar o job caro demais.
- **Matriz de sistemas operacionais ou de versões de Node.** O alvo é um iPhone e um usuário; a matriz multiplicaria minutos sem revelar nada. A cobertura de plataforma que interessa (WebKit e Chromium) já está nos projetos do Playwright.
- **Job separado por comando (um job para lint, outro para tipos, outro para testes).** Paraleliza, mas cada job repete `checkout` + `setup-node` + `npm ci` (~40 s cada), o que anula o ganho numa base deste tamanho.
- **`act` ou emulação local do Actions.** Dependência nova e imagem pesada para validar um arquivo de 60 linhas. Validação é o próprio push.
- **Codecov, Sentry, Lighthouse CI hospedado, ações de terceiros de "cache mágico".** Descartados por princípio (6), não por preço. Cobertura, quando interessar, sai do `vitest --coverage` com relatório lido no log ou em artefato interno.
- **Job de deploy para o Cloudflare Pages via `cloudflare/pages-action`.** Exigiria guardar `CLOUDFLARE_API_TOKEN` como secret e usaria ação de terceiro. A integração nativa do Pages com o GitHub (D10) faz o mesmo sem segredo no repositório.
- **Gerar os prints (D6) no CI e commitá-los de volta.** Precisaria de `permissions: contents: write` e de um push automático a cada execução — mais risco e mais ruído no histórico do que valor. Os prints são entregáveis de fim de fase, acionados à mão.
- **Cache de `~/.cache/ms-playwright` desde já.** Adiado, com gatilho objetivo (seção 4).
- **Fixar as ações por SHA** em vez de tag maior (`actions/checkout@v7`). É a recomendação de supply chain para repositório público com colaboradores. Aqui, num repositório privado de um autor e só com ações oficiais do GitHub, a tag maior traz correção de segurança automaticamente e custa menos manutenção. Reavaliar se o repositório virar público.

## Consequências

- Todo push de código passa a ter um veredito objetivo antes de qualquer revisão humana ou de agente. O `revisor` e o `revisor-critico` deixam de precisar perguntar "rodou o `verificar`?".
- O fluxo continua sendo push direto em `main` (**D8**). Sem proteção de branch, **o CI avisa, não impede**: quem faz o push precisa conferir a execução. Na prática, o orquestrador deve checar o resultado antes de fechar o item — hoje isso exige a interface do GitHub ou o `gh` (ver Pendências).
- O `ci.yml` vira o contrato de "o que precisa passar". Ferramenta nova no `package.json` sem passo no CI é ferramenta que ninguém roda.
- `.github/workflows/ci.yml` passa a ser propriedade do agente `dominio` (infraestrutura), complementando a tabela de propriedade do ADR 0002. Ajuste no passo de e2e pode vir junto do `testador`, mas sempre por este ADR.
- Minutos de Actions num repositório privado passam a ser um recurso a observar: estimados ~6 a 8 min por push de código, e zero em commit de documentação.
- O que fica de fora deste item: deploy (0.9), suíte de testes de verdade (0.4), prints (0.13), relatório de cobertura, auditoria de desempenho (5.5) e qualquer proteção de branch no GitHub.

## Pendências (ação do usuário, fora de arquivo)

1. **Proteção de branch.** Não é necessária para o CI funcionar, e **exigir status check hoje quebraria o fluxo**: com "require status checks", o GitHub recusa push direto em `main` (o commit ainda não tem execução verde), forçando tudo a virar pull request; e commits só de documentação, pulados pelo `paths-ignore`, ficariam eternamente "pendentes". Recomendação: **deixar sem proteção enquanto o fluxo for push direto** e tratar vermelho no CI como bloqueio de processo, não de plataforma. Se um dia o projeto passar a trabalhar por PR, aí sim vale ativar em Settings → Rules → Rulesets, exigindo `verificar` e `e2e`.
2. **Aviso de falha.** Por padrão o GitHub manda e-mail para o autor do commit quando a execução falha (Settings → Notifications → Actions). Confirmar que está ligado, já que ninguém fica olhando a aba Actions.
